## 1. src/wiggles_em/backends/pymol.py:294

**A view run with preserve_bfactors=False leaves no stash, so the next view stashes the already-overwritten column and its note claims those values are the originals. [same root cause also at: src/wiggles_em/bfactors.py:64]**

`_stash` returns after only a warning when `preserve_bfactors` is False, so `_STASH` stays empty; first-stash-wins in `stash_bfactors` therefore does not protect the next view, which reads `b` back from PyMOL after it has been clobbered. Reproduced: render a ColorByScalar on object 'm' with `PymolBackend(port, preserve_bfactors=False)` (real B-factors 11.0/22.0 destroyed, stash empty), then render another with `preserve_bfactors=True` on a port now reporting the overwritten values — the stash becomes {('m','1'): 0.9, ('m','2'): 0.3} (view A's scalar) and the note says "B-factor column overwritten. The original 2 values are held in this session; call restore_bfactors(port, 'm') to put them back." Calling `restore_bfactors` then writes 0.9/0.3 into the B-factor column and returns 'Restored 2 B-factors on m', permanently destroying the crystallographic values while reporting success — precisely the outcome the first-stash-wins docstring says it exists to prevent.

## 2. src/wiggles_em/atoms.py:45

**Atom identity was moved onto PyMOL's `index`, which is renumbered when atoms are removed; `rank` is the stable per-object ordinal and would have been unique too. [same root cause also at: src/wiggles_em/bfactors.py:103]**

occupancy_view colours 6xyz, so PymolBackend._stash saves {('6xyz','1'):b1, ('6xyz','2'):b2, ...} keyed on index. The user then runs `remove solvent` (or `remove hydro`), which is routine before a figure. PyMOL renumbers `index` over the remaining atoms. restore_bfactors then runs `alter 6xyz, b=stored.wiggles_b.get('|'.join((model, str(index))), b)` and every atom after the first deleted one receives a different atom's B-factor, while the returned string says 'Restored N B-factors on 6xyz'. That is silently writing one atom's value onto another — the exact failure Atom.key's docstring says the change was made to remove. `rank` is documented as the original input order and is not renumbered by removal, so (model, rank) is both unique per session and stable.

## 4. src/wiggles_em/backends/pymol.py:380

**When the host reports normalize_ccp4_maps off, _level_for demands a load_map record that ensemble frames never have, so latent_traverse_view cannot render at all. [same root cause also at: src/wiggles_em/backends/pymol.py:376]**

## 5. src/wiggles_em/backends/pymol.py:475

## 6. src/wiggles_em/backends/pymol.py:543

**The backend's lazy `normalisation_state(self.port)` read was deleted and replaced by a constructor argument that still defaults to None, and `draw()` cannot pass it — so an unnormalised session is silently treated as normalised. ## 7. src/wiggles_em/provenance.py:155

**Replacing the declaration-order `break` with longest-token-wins silently dropped the category priority, so network-enhanced maps are now suggested as merely SHARPENED. [same root cause also at: src/wiggles_em/provenance.py:155]**

The old loop scanned `_TOKENS` in declaration order — NN_ENHANCED, GENERATED, SHARPENED, MEASURED — and broke on the first category hit, which encoded a most-cautionary-first priority. `sorted(candidates, key=lambda pair: -len(pair[1]))` replaces that with raw token length, and 'postprocess' (11 chars, SHARPENED) is longer than 'emready' (7), 'locscale' (8) and 'cryolvm' (7). Reproduced: `postprocess_emready.mrc`, `postprocess_locscale.mrc` and `run_postprocess_cryolvm.mrc` all now report suggested=sharpened with reason "the name or labels contain 'postprocess', which suggests sharpened"; before the change all three gave nn_enhanced. These are the ordinary output names for running EMReady/LocScale/CryoLVM on a RELION postprocess map. The user is offered the SHARPENED banner ('features are easier to over-read than in the unsharpened map') instead of NN_ENHANCED ('Treat this map as a hypothesis, not a measurement'), and the whole point of the NN_ENHANCED category is that its warning is not interchangeable with sharpening.

## 9. src/wiggles_em/ensembles.py:195

**The rigid-motion detector fires on any tangential conformational change, so ensemble_spread_view tells a user their correctly-superposed measurement is not a conformational quantity. [same root cause also at: src/wiggles_em/ensembles.py:195]**

`radial_spread` is by its own docstring blind to tangential motion, and `rigid_dominated = positional > RIGID_RATIO * max(radial, 1e-9)` treats radial≈0 as proof of rigid motion. Reproduced with a counter-rotating twist (top ring +25°, bottom ring -25° — the ratchet/F1-ATPase class of real conformational change, not a rigid body motion): positional mean 2.16 Å, radial mean 7.9e-16 Å, ratio ~3e15, so the check fires regardless of RIGID_RATIO. With `superposed=True` the report prints '! RIGID-BODY MOTION DOMINATES … That gap is a rigid offset or rotation between the states, not flexibility … the number above is not a conformational quantity', instructing the user to refit already-fitted states and discard a correct measurement. Retuning 3.0→10.0 cannot fix this class because radial is exactly zero.
